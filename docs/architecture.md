# Архитектура решения

## 1. Общий обзор

Платформа-агрегатор ИТ-вакансий с обратной механикой подбора реализована как монолит
с явным разделением слоёв:

```
┌─────────────────────────────────────────────────────────────┐
│ Frontend: статический SPA (HTML/CSS/JS)                     │
│ public/index.html, public/js/, public/css/                  │
└──────────────────────────────┬──────────────────────────────┘
                               │ REST /api (JSON)
┌──────────────────────────────▼──────────────────────────────┐
│ Backend: Node.js + Express                                  │
│ server/index.js        — маршруты REST API                  │
│ server/matching.js     — категоризация и матчинг (правила)   │
│ server/testing.js      — движок тестирования кандидатов      │
│ server/services/fspMock.js — заглушка интеграции с ФСП      │
└──────────────────────────────┬──────────────────────────────┘
                               │ better-sqlite3
┌──────────────────────────────▼──────────────────────────────┐
│ Хранилище: SQLite (data/app.db)                             │
│ server/db.js — схема и миграции                             │
└─────────────────────────────────────────────────────────────┘
```

Дополнительно в репозитории:
- `src/` — Telegram-бот (Yandex Cloud Function, шаблон SourceCraft);
- `.sourcecraft/ci.yaml` — CI/CD для деплоя бота;
- `render.yaml` — Render Blueprint для деплоя веб-сервиса.

## 2. Компонентная архитектура

### 2.1 Backend-слой

| Модуль | Ответственность |
| --- | --- |
| `server/index.js` | HTTP-сервер, маршрутизация, валидация запросов, ответы |
| `server/db.js` | Подключение к SQLite, схема таблиц, лёгкие миграции |
| `server/matching.js` | Категоризация кандидатов, rule-based скоринг под вакансию |
| `server/testing.js` | Банк заданий, генерация тестов, оценка, правила смены грейда |
| `server/services/fspMock.js` | Заглушка API ФСП (контракт методов сохранён для реальной интеграции) |
| `server/seed.js` | Наполнение БД демо-данными (идемпотентно) |

### 2.2 Хранилище (SQLite)

Таблицы:
- `candidates` — профили соискателей (стек, заявленный грейд, роль, контакты,
  `verified_grade`, `last_grade_change`);
- `vacancies` — вакансии работодателей (стек, грейд, роль, зарплата «от–до»);
- `offers` — приглашения работодателя кандидату (статусы: pending/accepted/declined);
- `achievements` — проекция достижений ФСП для быстрых выборок;
- `test_attempts` — попытки тестирования кандидатов (вопросы, ответы, результат).

### 2.3 Frontend-слой

SPA на чистом JavaScript без сборки:
- `public/js/api.js` — тонкий REST-клиент;
- `public/js/app.js` — рендер и события;
- `public/index.html` — разметка с вкладками: Кандидаты, Тестирование, Вакансии, Подбор, Офферы;
- `public/css/styles.css` — тёмная тема в цветовой гамме, близкой к фирменному стилю ФСП.

## 3. Основные пользовательские сценарии

### 3.1 Соискатель

1. Регистрация/создание профиля (ФИО, стек, роль, грейд, опыт, контакты, опционально ID ФСП).
2. Прохождение тестирования: выбор специализации и заявляемого грейда → генерация теста
   → ответы → результат.
3. По результату теста определяется подтверждённый грейд (`verified_grade`), который виден
   работодателю; при уверенном прохождении грейд может быть повышен, при неудаче —
   не понижается (можно пройти уровень ниже).
4. Смена грейда ограничена cooldown 90 дней.
5. Получение офферов от работодателей, принятие/отклонение.

### 3.2 Работодатель

1. Публикация вакансии (стек, грейд, роль, зарплата «от–до»).
2. Получение подборки: система ранжирует кандидатов по подтверждаемому профилю
   (категория = связка «специализация + грейд», подтверждённая тестом и достижениями ФСП).
3. Выход на контакт: направление оффера конкретному кандидату с зарплатой.
4. Контактные данные кандидата раскрываются только после принятия оффера (в MVP
   реализовано частично — см. раздел «Ограничения MVP»).

## 5. Развёртывание

### Локально

```bash
npm install
npm run seed
npm start
```

### Render (Blueprint)

`render.yaml` создаёт веб-сервис:
- build: `npm install`;
- start: `npm run seed && npm start`;
- health check: `/api/health`.

### Docker

В репозитории есть `Dockerfile` и `docker-compose.yml` (см. `docs/deployment.md`).

## 6. Безопасность и приватность

- Пароли/токены в MVP не хранятся: авторизация реализуется на следующем этапе.
  Для ФСП-интеграции предусмотрена совместимость с Keycloak (OIDC).
- Контактные данные кандидата не должны показываться работодателю до принятия
  приглашения (в MVP — ограничение на уровне API-логики офферов).
- Все данные — синтетические (демо), публикация профилей регулируется согласием
  пользователя (см. `docs/privacy.md`).
- Требования 152-ФЗ учтены концептуально: согласие на обработку, разграничение прав,
  безопасное хранение токенов (детали — в разделе «Развитие»).

## 7. Ограничения MVP и направления развития

- Нет полноценной аутентификации (email + подтверждение) — следующий этап.
- Нет ролевых личных кабинетов — сейчас единый интерфейс для демонстрации.
- PDF-профиль и автораспознавание резюме — следующий этап.
- Регулярные короткие задания — концепция описана в `docs/testing.md`.
- Защита от фиктивных вакансий и интеграция с ATS — концепция в `docs/roadmap.md`.
