# Интеграция с реестром ФСП

## 1. Текущее состояние (MVP)

Доступа к API ФСП в рамках хакатона нет, поэтому в репозитории реализована заглушка
`server/services/fspMock.js`. Она хранит синтетические достижения участников и
предоставляет два метода:

- `getDisciplines()` — список дисциплин ФСП;
- `getAchievements(fspId)` — достижения участника по ID ФСП.

Контракт методов сохранён: при подключении реального API достаточно заменить
реализацию модуля без изменения остального кода.

## 2. Предполагаемая схема интеграции

```
┌──────────────┐   REST/OIDC   ┌──────────────────┐
│ Наша платформа│ ───────────► │ Реестр ФСП        │
│              │ ◄─────────── │ (Keycloak + API)  │
└──────────────┘              └──────────────────┘
```

### 2.1 Аутентификация (совместимость с Keycloak)

ФСП ID будет работать на базе Keycloak (OIDC). Для совместимости предлагается:

- использовать стандартный OIDC Authorization Code Flow;
- наш сервис регистрируется как клиент Keycloak (confidential client);
- пользователь входит через ФСП ID; токены (access + refresh) хранятся на сервере
  в зашифрованном виде (или в HttpOnly cookie);
- профиль кандидата получает поле `fsp_sub` (subject из Keycloak), связывающее учётную
  запись платформы с ID ФСП.

Альтернативный путь (если интеграция не готова): собственная регистрация по email с
подтверждением; привязка ID ФСП выполняется позже через форму «Связать с ФСП».

### 2.2 Получение достижений

Предполагаемый контракт API ФСП (гипотеза, уточняется после предоставления
спецификации):

```
GET /api/v1/participants/{fspId}/achievements
Authorization: Bearer <service-token>

Response:
{
  "participant_id": "FSP-0001",
  "achievements": [
    {
      "id": "ach-123",
      "discipline": "algorithm",
      "competition": "Кубок ФСП ...",
      "result": "1 место",
      "role": "Участник",
      "rank": "КМС",
      "year": 2024,
      "verified": true
    }
  ]
}
```

Наш сервис мапит ответ в структуру, совместимую с `fspMock.js`, и сохраняет проекцию
в таблицу `achievements` для быстрых выборок.

### 2.3 Обработка отсутствия истории ФСП

Обязательное требование ТЗ: корректная обработка случая, когда истории ФСП у кандидата
нет. Реализовано так:

- `getAchievements(fspId)` возвращает `[]` для неизвестного/пустого ID;
- категория кандидата строится без учёта достижений (`verified: false`);
- UI показывает «Без ФСП» и не блокирует тестирование и подбор;
- работодатель может фильтровать по наличию достижений, но не обязан это делать.

### 2.4 Безопасность интеграции

- Сервис-клиент использует client credentials с ограниченной областью (scope)
  `achievements:read`;
- токены хранятся в защищённом хранилище (env / секрет-менеджер), не в коде;
- все запросы к ФСП логируются (audit) без чувствительных данных;
- 152-ФЗ: получение достижений возможно только при наличии согласия кандидата на
  обработку и публикацию данных профиля.
