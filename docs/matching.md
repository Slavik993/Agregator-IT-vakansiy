# Механика подбора и категоризация кандидатов

## 1. Принцип

Выдача формируется на основании **категорий, присвоенных по итогам опроса и
тестирования**, а не на основании самоописанных данных резюме.

Категория — это группа однотипных соискателей, в основе которой связка
**специализация + грейд** (например, «backend-разработчики с опытом»). Внутри категории
кандидаты ранжируются: выше — те, у кого сильнее подтверждённый профиль (лучше результат
теста, есть достижения ФСП).

## 2. Категоризация

Реализована в `server/matching.js` (`categorizeCandidate`):

```
category = {
  stack: [нормализованный список технологий],
  grade: effectiveGrade,
  role,
  work_format,
  city
}
```

- Стек нормализуется (lowercase, trim, split по запятой).
- Заявленный грейд может быть **повышен** за подтверждённые достижения ФСП:
  - junior + ≥1 достижение → middle;
  - middle + ≥2 достижения → senior.
- Подтверждённый грейд из теста (`verified_grade`) имеет приоритет над заявленным
  при построении категории.

## 3. Скоринг кандидата под вакансию (0–100)

`scoreCandidate` в `server/matching.js`:

| Фактор | Максимум |
| --- | --- |
| Пересечение стека | 60 |
| Совпадение грейда (разница 1 уровень — 12) | 25 |
| Совпадение роли | 10 |
| Подтверждённые достижения ФСП | 5 |
| **Итого** | **100** |

Функция возвращает `{ score, breakdown }`, где `breakdown` — разбивка баллов
по компонентам (`stack`, `grade`, `role`, `fsp`). Это обеспечивает объяснимость выдачи:
работодатель видит, за что именно кандидат получил баллы.

Кандидаты с нулевым скорингом отфильтровываются, остальные сортируются по убыванию.
При равном скоринге выше оказывается кандидат с большим числом подтверждённых
достижений ФСП.

## 4. Объяснимость выдачи

Каждый элемент подборки содержит `category` (стек, грейд, роль, формат, город),
`verified` (есть ли достижения ФСП), `gradeBoosted` (повышен ли грейд за достижения),
`score` и `breakdown` (вклад каждого фактора в итоговый балл). Это позволяет
работодателю понять, почему кандидат попал в подборку: совпал стек, грейд, роль,
либо добавлены баллы за подтверждённые достижения.

## 5. Поиск по банку кандидатов с фильтрами

Эндпоинт `GET /api/candidates/search` даёт доступ ко всей базе с фильтрацией:

| Параметр | Описание |
| --- | --- |
| `role` | Специализация (backend, frontend, ml, …) |
| `grade` | Категория/грейд (junior, middle, senior, lead) |
| `stack` | Стек через запятую (пересечение хотя бы одной технологии) |
| `work_format` | Формат работы (office, hybrid, remote) |
| `city` | Город |
| `fsp_only` | `true` — только кандидаты с подтверждёнными достижениями ФСП |

Фильтры применяются к уже категоризированному списку, не пересчитывая категории:
уточнение запроса не теряет ранее полученную подборку. Для каждого результата
рассчитывается `rank` — сила подтверждённого профиля (см. раздел 7).

## 6. Выход на контакт (обратная механика)

Сценарий отличается от классического отклика:

1. Работодатель описывает потребность (вакансия) и получает подборку.
2. Работодатель выбирает конкретного кандидата и отправляет **оффер** с описанием
   предложения и уровнем зарплаты.
3. Кандидат видит условия **до начала общения** и принимает/отклоняет оффер.
4. Статусы оффера: `pending` → `accepted` / `declined`.

Контактные данные кандидата раскрываются работодателю только после принятия оффера
(в MVP: поле telegram скрывается до статуса `accepted`).

## 7. Ранжирование внутри категории

Формула позиции внутри категории (`rankInCategory` в `server/matching.js`):

```
rank = min(тестовый_балл, 70) + min(достижения_ФСП * 10, 30)
```

- тестовый сигнал: лучший процент завершённых тестов кандидата (до 70 баллов);
- ФСП-сигнал: до 30 баллов за подтверждённые достижения (по 10 за каждое,
  максимум 3).

Итоговый ранг — целое число 0..100. В подборке по вакансии (`/matches`) кандидаты
ранжируются скорингом под вакансию; при равном скоринге выше оказывается кандидат
с большим числом подтверждённых достижений ФСП.
