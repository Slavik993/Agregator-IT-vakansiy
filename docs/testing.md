# Механика тестирования кандидатов

## 1. Проблема

Единый фиксированный набор заданий не подходит: он быстро разойдётся между участниками
рынка, и оценка перестанет быть объективной. Генерация полностью уникальных заданий
нейросетью не гарантирует сопоставимую сложность и дискриминативность.

## 2. Предложенная механика

Используется **комбинированный подход «банк заданий + параметрическая генерация»**:

### 2.1 Банк заданий по специализациям и грейдам

Задания хранятся в `server/testing.js` (`TEST_BANK`) и размечены по связке
«специализация + грейд» (backend/frontend/ml × junior/middle/senior). Каждое задание
имеет вес (junior=1, middle=2, senior=3) — это позволяет считать взвешенный балл.

### 2.2 Случайная выборка

Тест собирается **случайной выборкой** из банка для конкретной пары
«роль + заявляемый грейд»:

- 3 задания заявляемого грейда;
- 1 задание уровнем ниже (проверка базы);
- 1 задание уровнем выше (проверка готовности к повышению).

Таким образом, два кандидата с высокой вероятностью получают разные наборы вопросов,
а утечка одного набора не даёт преимущества при следующем прохождении.

### 2.3 Параметрические задания

Часть заданий имеет `kind: 'param'`: генератор создаёт уникальные числовые данные для
каждого кандидата (например, «бинарный поиск по массиву из N элементов», где N случайно).
Даже зная формулировку, кандидат должен решить задачу заново — выучить ответ
«наизусть» невозможно.

### 2.4 Перемешивание вариантов

Варианты ответов перемешиваются при каждой генерации теста, а индекс правильного
ответа пересчитывается. Заучивание позиции варианта не работает.

### 2.5 Оценка и грейд

Процент = сумма весов верных ответов / сумма весов всех вопросов × 100.

| Результат | Порог | Действие |
| --- | --- | --- |
| `confident` | ≥ 85% | Грейд может быть повышен на один уровень |
| `passed` | 55–84% | Заявленный грейд подтверждается |
| `not_passed` | < 55% | Грейд не подтверждён; кандидат может пройти уровень ниже |

Грейд **принудительно не понижается**: при неудаче сохраняется предыдущий
подтверждённый грейд (`verified_grade`), а `last_grade_change` обновляется только при
фактической смене.

### 2.6 Cooldown смены грейда

Смена грейда ограничена **90 днями** (`GRADE_CHANGE_COOLDOWN_DAYS`). Эндпоинт
`GET /api/candidates/:id/grade-change-status` возвращает доступность смены и дату,
когда она станет возможной.

## 3. Устойчивость к распространению заданий

| Угроза | Защита |
| --- | --- |
| Кандидат выучил ответы на фиксированный набор | Случайная выборка из банка: наборы разные |
| Кандидат запомнил формулировку параметрического задания | Числовые данные генерируются заново каждый раз |
| Кандидат запомнил позицию правильного варианта | Варианты перемешиваются при генерации |
| Ответы разошлись по рынку | Банк шире выдаваемого набора; параметрические задачи не имеют «готового» ответа |

Ограничение метода: при очень большом числе попыток возможен сбор полного банка.
Для продакшена предлагается добавить:
- пул заданий, пополняемый редактором/LLM с ручной валидацией сложности;
- ограничение числа попыток в месяц;
- динамическую подстройку сложности (CAT — computer adaptive testing).

## 4. Регулярные короткие задания (концепция, за рамками MVP)

Система периодически (например, раз в 2 недели) предлагает кандидату короткую задачу
от работодателя — решить её или предложить подход. Результат влияет на «актуальность»
профиля: свежий сигнал повышает позицию кандидата в ранжировании внутри категории.

Реализация: таблица `challenge_attempts`, планировщик (cron), интеграция с офферами —
работодатель может прикрепить задачу к офферу.
