# Механика тестирования кандидатов

## 1. Устойчивость к распространению заданий

ТЗ §2 накладывает ограничения на механику тестирования:
- единый набор заданий **не подходит** — разойдутся между участниками рынка;
- генерация уникальных заданий нейросетью **не гарантирует** сопоставимую сложность.

Используем **гибридную** механику, устойчивую к обеим проблемам:

1. **Банк заданий шире, чем выдача.** За каждый тест выдаётся 5 вопросов из пула
   по 5 заданий на каждую (роль × грейд) комбинацию.
2. **Случайная выборка.** Каждый запуск `generateTest(role, claimedGrade)`
   перемешивает банк и берёт 3 задания заявленного грейда + по одному соседнего
   уровня (ниже/выше), добивая до 5 из оставшихся того же грейда.
3. **Перемешивание вариантов.** `shuffle(options)` при каждой генерации, чтобы
   правильный ответ оказывался в случайной позиции.
4. **Параметрические задания.** `kind: 'param'` — генератор с уникальными
   числовыми данными на каждый запуск (значения `i`, `N`, `P`, `R` и т. п.
   выбираются случайно в разумном диапазоне).
5. **Cooldown смены грейда — 90 дней.** `GRADE_CHANGE_COOLDOWN_DAYS = 90`
   (см. `resolveGrade` и `canChangeGrade`).
6. **Грейд принудительно не понижается.** При `result === 'not_passed'`
   сохраняется предыдущий подтверждённый грейд, кандидату предлагается пройти
   тест уровнем ниже.

Эти меры делают публикацию одного скриншота малоценной: конкретные числа и
порядок вариантов будут другими уже при следующей попытке.

## 2. Правила оценки

| Диапазон | Результат | Действие |
| --- | --- | --- |
| `>= 85%` | `confident` | Грейд повышается на 1 (если не cooldown) |
| `55–84%` | `passed` | Заявленный грейд подтверждается |
| `< 55%` | `not_passed` | Грейд **не понижается**, предлагается уровень ниже |

Эти же пороги (`PASS_THRESHOLD = 55`, `CONFIDENT_THRESHOLD = 85`) используются
при валидации.

## 3. Cooldown и смена грейда

- `canChangeGrade(candidate)` проверяет, прошло ли 90 дней с последней смены.
- При попытке повышения во время cooldown: `grade_changed=false`,
  `cooldown_blocked=true`, в ответе приходит `cooldown_days=90`.

## 4. Банк заданий

- `server/testing.js: TEST_BANK` — массив из 45 заданий по ролям `backend`,
  `frontend`, `ml` и грейдам `junior/middle/senior`.
- Каждый вопрос имеет вес (`weight: 1|2|3`) по грейду: junior = 1, middle = 2,
  senior = 3.
- Валидация (`validate.js`) проверяет дискриминативность и монотонность среднего
  процента по истинному грейду.

## 5. Дискриминативность

На синтетических кандидатах с известным «истинным» грейдом
(`server/validate.js`):

- Доля попыток с подтверждённым грейдом (`>= 55%`) ≈ 80–95%.
- Монотонность среднего процента: junior < middle < senior.
- Конкретные значения зависят от seed-данных; при изменении банка заданий
  рекомендуется пересмотреть пороги `PASS_THRESHOLD` / `CONFIDENT_THRESHOLD`.

## 6. Сохранение результатов

В `test_attempts` сохраняются:
- `questions` (JSON) — конкретные сгенерированные вопросы и варианты;
- `answers` (JSON) — выбранные индексы;
- `score`, `max_score`, `percent`;
- `result` (`confident|passed|not_passed`);
- `grade_after` — грейд, который следует за `candidate.grade`/`verified_grade`;
- `completed_at`.

Это даёт возможность воспроизвести и проанализировать любую попытку.
